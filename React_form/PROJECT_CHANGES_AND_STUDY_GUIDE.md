# College Management System - Study & Viva Guide

## 1. Technologies

*   **React:** A JavaScript library for building user interfaces. **Why:** Allows building a fast, Single-Page Application (SPA) where only specific components update without full page reloads. **Where:** Used for the entire frontend (Dashboard, Modals, Forms).
*   **TypeScript:** Adds static typing to JavaScript. **Why:** Catches errors during development (e.g., passing a string where a number is expected) rather than at runtime. **Where:** Used across the entire frontend (e.g., `Assignment`, `SubmissionFile` types).
*   **Redux Toolkit (RTK) / RTK Query:** A state management and data-fetching library. **Why:** Simplifies fetching, caching, and updating API data. If you change a component, RTK Query provides cached data instantly. **Where:** Used in `baseQueryWithReauth.ts` and `assignmentApi.ts` for all API calls except file uploads.
*   **Axios:** A promise-based HTTP client. **Why:** RTK Query doesn't natively support tracking upload progress. Axios has `onUploadProgress`, making it easy to create a real-time progress bar. **Where:** Used specifically in `FileUpload.tsx`.
*   **React Router:** A routing library for React. **Why:** Allows navigation between different views (Dashboard, Login, Classes) without refreshing the page. **Where:** Used to define protected routes and app navigation.
*   **ASP.NET Core (Web API):** A cross-platform framework for building backend APIs. **Why:** Highly scalable, secure, and performant backend to handle business logic. **Where:** The entire backend server (`ReactFormApi`).
*   **Entity Framework Core (EF Core):** An Object-Relational Mapper (ORM). **Why:** Allows interacting with the database using C# code (LINQ) instead of writing raw SQL queries. **Where:** Used in the backend to query and save data.
*   **SQL Server:** A relational database management system. **Why:** Provides robust, structured data storage with strict relationships (Foreign Keys). **Where:** The primary database for the application.
*   **ASP.NET Core Identity:** A built-in API for managing users, passwords, and roles. **Why:** Handles password hashing, security, and role-based access control out of the box. **Where:** Handles User Registration, Login, and Roles.
*   **JWT (JSON Web Token):** A secure string used to verify a user's identity. **Why:** Stateless authentication. The server doesn't need to look up the database on every request to know who you are. **Where:** Created on login, sent with every API request.
*   **HttpOnly Cookies:** A type of browser cookie that JavaScript cannot access. **Why:** Protects JWT tokens from Cross-Site Scripting (XSS) attacks. **Where:** Tokens are stored here instead of LocalStorage.
*   **TailwindCSS / Lucide-React:** A utility-first CSS framework and an icon library. **Why:** Rapid UI styling without writing custom CSS files. **Where:** Used to style every frontend component.

## 2. Backend Structure

*   **Models (Entities):** C# classes that represent database tables (e.g., `Assignment`). **Why:** Defines the structure of the data and relationships.
*   **DTOs (Data Transfer Objects):** Stripped-down versions of models. **Why:** To send only the necessary data to the frontend, hiding sensitive information (like passwords or internal IDs) and avoiding circular reference errors.
*   **Controllers:** The entry points for API requests (e.g., `AssignmentsController`). **Why:** Receives HTTP requests, performs authorization checks, processes data, and returns HTTP responses (`200 OK`, `403 Forbidden`).
*   **DbContext (`AppDbContext`):** The bridge between C# and SQL Server. **Why:** Manages database connections and translates C# LINQ queries into SQL.
*   **Migrations:** Code files generated by EF Core. **Why:** Tracks changes made to models and updates the database schema accordingly (e.g., creating a new table).
*   **Dependency Injection (DI):** A design pattern used in ASP.NET Core. **Why:** Instead of manually creating objects (e.g., `new AppDbContext()`), the framework "injects" them where needed (like inside Controller constructors). This makes code testable and loosely coupled.

## 3. Database — Important

*   **Provider:** SQL Server
*   **ORM:** Entity Framework Core

### Complete List of Important Tables

**Identity Tables:**
*   **`AspNetUsers`** (`ApplicationUser`): Stores all users. Columns: `Id` (string/Guid), `Email`, `PasswordHash`, `FullName`.
*   **`AspNetRoles`**: Stores roles (Admin, Teacher, Student).
*   **`AspNetUserRoles`**: Links users to roles (Many-to-Many).

**Application Tables:**
*   **`ClassChannels`**: Represents a classroom.
    *   *Columns:* `Id` (int, PK), `Name`, `Description`, `CreatedByUserId` (FK to Users).
*   **`ClassEnrollments`**: Links users to classes and tracks their specific role in that class.
    *   *Columns:* `Id` (PK), `ClassChannelId` (FK), `ApplicationUserId` (FK), `RoleInClass` (string).
    *   *Relationship:* Many-to-Many between Users and Classes.
*   **`Assignments`**: Coursework created by a teacher.
    *   *Columns:* `Id` (PK), `ClassChannelId` (FK), `Title`, `Description`, `DueDate`, `CreatedByUserId`.
    *   *Relationship:* Belongs to a ClassChannel. Cascade delete on ClassChannel deletion.
*   **`AssignmentAttachments`**: Files uploaded by the teacher for an assignment.
    *   *Columns:* `Id` (PK), `AssignmentId` (FK), `FileName`, `StoredFileName`, `ContentType`, `FileSize`.
    *   *Relationship:* Belongs to Assignment. Cascade delete on Assignment deletion.
*   **`AssignmentSubmissions`**: A student's response to an assignment.
    *   *Columns:* `Id` (PK), `AssignmentId` (FK), `StudentUserId` (FK), `SubmittedText`, `Status`, `Grade`, `Feedback`.
    *   *Constraint:* Unique index on `[AssignmentId, StudentUserId]` (one submission per student).
*   **`SubmissionFiles`**: Files uploaded by the student for their submission.
    *   *Columns:* `Id` (PK), `AssignmentSubmissionId` (FK), `FileName`, `StoredFileName`, `ContentType`, `FileSize`.
    *   *Relationship:* Belongs to AssignmentSubmission. Cascade delete.

## 4. Authentication Flow

**Technologies:** Identity + JWT + HttpOnly Cookies.

**Flow:**
1.  **Login:** User sends email/password. Backend verifies via Identity.
2.  **Tokens Generated:** Backend generates a short-lived **Access Token** (e.g., 15 mins) and a long-lived **Refresh Token** (e.g., 7 days).
3.  **Cookies:** Backend sends tokens back in **HttpOnly cookies**. (Browser automatically attaches them to future requests).
4.  **Token Refresh:** When the Access Token expires (returning `401 Unauthorized`), the RTK Query `baseQueryWithReauth` catches it, sends the Refresh Token to `/Auth/refresh`, gets a new Access Token cookie, and retries the original request automatically.
5.  **Logout:** Backend clears the cookies.

*   `401 Unauthorized`: You are not logged in (missing/invalid token).
*   `403 Forbidden`: You are logged in, but don't have permission (e.g., wrong role).

## 5. Authorization

The system uses **Two-Layer Authorization**:

1.  **Global Role-Based:** (Admin, Teacher, Student). Ensures a Student cannot access the Admin dashboard.
2.  **Class/Channel-Based (Ownership):** Handled by `CheckClassAuthAsync` in controllers.
    *   **Why:** Being a "Teacher" globally isn't enough. A teacher should only be able to upload assignments to *their own* class.
    *   **How:** The controller checks `ClassEnrollments` to verify if the specific `UserId` is enrolled in the `ClassChannelId` with the role "Teacher".
    *   **Student Rule:** Students can only view assignments for classes they are enrolled in, and can only edit/delete files for their *own* `StudentUserId` submission.

## 6. Important Backend Methods

*   **`Where(x => ...)`**: Translates to a SQL `WHERE` clause. **Why:** To filter data (e.g., get assignments only for a specific class).
*   **`Include()` / `ThenInclude()`**: Eager loading. Translates to SQL `JOIN`. **Why:** To fetch related data. E.g., fetch an Assignment AND its Attachments in one query.
*   **`FindAsync(id)`**: **Why:** Quickly finds an entity by its Primary Key. Optimized to check local memory before hitting the database.
*   **`FirstOrDefaultAsync()`**: Returns the first item matching a condition or `null`. **Why:** Used when looking up a specific submission by StudentId.
*   **`AnyAsync()`**: Returns a boolean. **Why:** Highly efficient way to check if a record exists without downloading the actual record.
*   **`SaveChangesAsync()`**: **Why:** Commits all tracked inserts/updates/deletes to the SQL database in a single transaction.
*   **`IFormFile`**: C# interface representing an uploaded file. **Why:** Provides the file stream, `FileName`, and `Length` directly from the HTTP request.
*   **`PhysicalFile()`**: **Why:** A controller method that returns a file directly from the hard drive as an HTTP response (used for downloading attachments).
*   **`Guid.NewGuid().ToString()`**: **Why:** Generates a random, unique string (e.g., `a1b2c3d4...`). Used to rename files on the server to prevent naming conflicts and path traversal attacks.

## 7. Assignments Workflow

1.  **Teacher Creates:** Teacher creates an `Assignment` linked to a `ClassChannel`.
2.  **Teacher Attaches Files:** Teacher uploads reference files (`AssignmentAttachments`).
3.  **Student Views:** Student sees the assignment and state is implicitly "Assigned".
4.  **Student Uploads/Drafts:** Student uploads files (`SubmissionFiles`) with a progress bar. State remains "Assigned".
5.  **Turn In:** Student clicks Turn In. State changes to `"Turned In"`. `SubmittedAt` timestamp is set.
6.  **Teacher Reviews:** Teacher sees submissions.
7.  **Graded & Returned:** Teacher assigns a Grade/Feedback. State changes to `"Returned"`.
8.  **Lockdown:** Once "Returned", the backend blocks the student from uploading or deleting files.

## 8. File Uploads

**Two distinct systems:**
1.  **Teacher Reference Materials** (`AssignmentAttachments`)
2.  **Student Submissions** (`SubmissionFiles`)

**Rules & Architecture:**
*   **Storage:** Stored physically on the server hard drive (`Uploads/AssignmentAttachments`), NOT in the database. The database only stores metadata (FileName, ContentType, FileSize). **Why:** Storing large files in SQL makes the database huge and slow.
*   **GUID Filenames:** Original filename is ignored for storage. A GUID is used. **Why:** Prevents Path Traversal hacks (e.g., a hacker naming a file `../../windows/system32/cmd.exe`) and prevents students from overwriting each other's files.
*   **Validation:** Checked on backend. 20 MB size limit, 10 file count limit, restricted extensions (`.pdf, .jpg, .docx`, etc.).
*   **Authorization:** The backend physically checks if the user has rights to the class/submission before calling `System.IO.File.Delete()` or returning the file stream.

## 9. Frontend 

*   **React State (`useState`):** Holds temporary data. **Where:** Holding the typed text in a form before submitting, or holding the file upload progress percentages.
*   **RTK Query:** **What:** A data fetching tool. **Why:** Automatically caches API responses. If you switch tabs and come back, it loads instantly from cache.
*   **Axios:** **Why:** Used for the `FileUpload` component because it provides an `onUploadProgress` event, which RTK Query lacks. This allows the real-time progress bar.
*   **Protected Routes:** A React component wrapper that checks the Redux auth state. If `role` is null, it forces a redirect to `/login`.

## 10. Business & Security Rules (Backend Checklist)

*   [x] JWTs are strictly passed via HttpOnly cookies to prevent XSS.
*   [x] Users can only fetch data for classes they are explicitly enrolled in (`ClassEnrollments`).
*   [x] Teachers can only create/grade assignments in their assigned classes.
*   [x] Students can only delete/upload files for their *own* `StudentUserId` submission.
*   [x] File system paths are sanitized using GUIDs to prevent Path Traversal.
*   [x] Physical files are permanently deleted from the hard drive when their database record is deleted (saving space).
*   [x] Submissions marked as "Returned" are locked and cannot be modified or deleted by the student.

## 11. Viva Questions & Answers

### React & TypeScript
**Q: Why use React instead of standard HTML/JS?**
> A: React builds Single-Page Applications (SPAs). It updates the DOM efficiently using the Virtual DOM, meaning the page doesn't reload when switching tabs, resulting in a faster user experience.

**Q: Why use TypeScript instead of JavaScript?**
> A: TypeScript adds static typing. It catches errors at compile-time instead of runtime, ensuring my frontend components pass the correct data types to my backend API.

### Redux / RTK Query & Axios
**Q: Why use RTK Query for data, but Axios for file uploads?**
> A: RTK Query is excellent for caching JSON data, but it lacks native support for tracking upload progress. I used Axios specifically for file uploads to access `onUploadProgress` to build the real-time progress bar.

### ASP.NET Core & EF Core
**Q: What is Dependency Injection?**
> A: It's a design pattern where the framework provides objects (like the `AppDbContext`) to controllers automatically, rather than creating them manually with the `new` keyword. It makes the code testable and loosely coupled.

**Q: Why use Entity Framework (EF) Core?**
> A: EF Core is an ORM. It allows me to interact with the SQL database using C# objects and LINQ queries instead of writing vulnerable, raw SQL queries.

### Authentication & Authorization
**Q: How did you secure your JWT tokens?**
> A: I stored them in HttpOnly cookies instead of LocalStorage. This prevents malicious JavaScript (XSS attacks) from reading and stealing the tokens.

**Q: How does your Class Authorization work?**
> A: Global roles (like 'Teacher') aren't enough. My controllers verify the user's `Id` against the `ClassEnrollments` table to ensure they actually belong to the specific class they are trying to modify.

### File Uploads
**Q: Why save files to the file system instead of the database?**
> A: Storing raw binary data in a SQL database causes it to bloat and slow down. The file system is meant for files; the database just stores the metadata and the path.

**Q: What is Path Traversal and how did you prevent it?**
> A: It's a vulnerability where an attacker uses a malicious filename (like `../system/file`) to overwrite server files. I prevented this by completely ignoring the user's filename on the server and saving the file using a generated `GUID`.

## 12. Most Important Things to Remember

1.  **The Flow:** Request -> Controller -> Auth Check -> DbContext -> Database -> Response.
2.  **HttpOnly Cookies:** They stop JavaScript from reading the JWT. (Anti-XSS).
3.  **Include():** It's required in EF Core to fetch related table data (JOINs).
4.  **GUIDs for Files:** The ultimate protection against file overwrites and path traversal.
5.  **Ownership Check:** Always checking `StudentUserId == currentUserId` before allowing edits.
